HOTEL BOOKING MANAGEMENT SYSTEM
ENGINEERING AND MAINTENANCE GUIDE
Comprehensive reference for developers, reviewers, and future maintainers

===============================================================================
0. DOCUMENT PURPOSE AND READING ORDER
===============================================================================

This is the detailed engineering reference for the current codebase. It explains
why classes and functions exist, how data moves through the program, which rules
are authoritative, and where a future change must be made. It is intentionally
more detailed than README.md and ARCHITECTURE.md.

Recommended reading order for a new developer:
1. Read sections 1 to 4 for program startup, ownership and architecture.
2. Read sections 5 to 8 before changing booking, customer, room or invoice logic.
3. Read sections 9 to 11 before touching SQLite, reports or UI.
4. Read sections 12 to 15 before designing a feature or reviewing a pull request.

Scope statement:
- The program is a C++17 / Qt6 desktop application for internal hotel staff.
- It manages rooms, customers, reservations, explicit check-in/check-out,
  invoices, maintenance, dashboard reporting and local SQLite persistence.
- It is not a public booking engine, real payment system, real notification
  service, multi-property server, or complete staff identity system.

Important terms:
- planned arrival/departure: Booking::checkInDate and checkOutDate.
- actual arrival/departure: staff-recorded actualCheckInDate/actualCheckOutDate.
- active stay: a guest has explicitly checked in; the calendar never creates it.
- half-open date interval: [startDate, endDate). End date is available again.
- archived record: retained history excluded from normal operational use.
- snapshot: historical values copied at a specific business event and not later
  recomputed from mutable entities.

===============================================================================
2. STARTUP, LOGIN, EVENT LOOP AND SHUTDOWN
===============================================================================

Exact execution path in main.cpp:

1. QApplication app(argc, argv) is constructed.
2. HotelManager hotelManager is created on the stack. It outlives MainWindow and
   every child widget, so it is the single live in-memory hotel aggregate.
3. resolveDatabasePath() starts from QDir::currentPath(), walks upward until both
   CMakeLists.txt and src exist, creates <project>/data, and returns
   <project>/data/hotel_data.db. This avoids creating a separate DB inside a
   build directory when the executable is launched from there.
4. DataManager::getInstance().loadAll(hotelManager, databasePath) opens SQLite,
   initializes/migrates schema, reconciles legacy duplicate data, and restores
   all valid data into HotelManager. On failure main shows a critical error and
   exits before opening operational UI.
5. LoginWindow runs with exec(). If rejected, the program exits. If accepted,
   StaffSession has been initialized for the process.
6. MainWindow mainWindow(&hotelManager) is constructed and shown.
7. app.exec() runs the Qt event loop. Signals, slots, dialogs and table actions
   route user intent to services and then persistence.
8. After the event loop returns, DataManager::saveAll is called as an exit
   safeguard. It does not replace immediate transactional workflow commits.

Lifetime rule:
Do not create a second HotelManager for a dialog, page, test shortcut, or second
window. It would hold separate data from the loaded aggregate and would make UI,
database and report results diverge.

MainWindow composition:
- Owns the Qt shell and page widgets.
- Creates DashboardWidget, ReservationsPageWidget, CustomerPageWidget,
  RoomPageWidget and RoomStatusPageWidget with the same HotelManager pointer.
- Uses QStackedWidget for navigation.
- Does not own business rules; it routes navigation and refresh signals only.

Important signal wiring:
- RoomStatusPageWidget::bookingRequested(roomNumber) switches to Reservation
  page, refreshes it and starts a preselected-room booking dialog.
- ReservationsPageWidget::bookingChanged refreshes Room Status and Dashboard.
- ReservationsPageWidget::bookingCompleted refreshes Dashboard history and Room
  Status after persisted checkout.
- roomStatusBookingCancelled returns the Room Status booking flow to its origin.

===============================================================================
3. AUTHENTICATION CONTEXT
===============================================================================

LoginWindow is a modal QDialog created in src/views/LoginWindow.*. setupUi()
builds a compact sign-in form. attemptLogin() trims username, rejects empty input,
hashes password text with SHA-256 and compares it with the bootstrap digest.
Success starts:

  StaffSession::instance().start("admin", "Administrator", "Administrator")

StaffSession is a singleton whose public API is:
  instance()
  start(username, displayName, role)
  clear()
  isAuthenticated()
  username()
  displayName()
  role()

It exists to supply a current actor context for future audit logging. It does not
store a password.

Security limitation:
The existing account is a classroom bootstrap only. A fixed unsalted SHA-256 hash
is not a production password solution. There are no persisted staff accounts,
individual credentials, password-reset policy, rate limits, lockout, enforced
role permissions, or immutable audit log. Future production design needs a Staff
table, per-user salted Argon2/bcrypt hashes, authorization at service boundaries,
and AuditLog records.

===============================================================================
4. ARCHITECTURE, OWNERSHIP AND DESIGN INTENT
===============================================================================

Mutation path:

Qt view
  -> HotelManager facade
       -> BookingManager -> BookingService and InvoiceService
       -> CustomerManager -> CustomerService
       -> RoomManager -> RoomService

Read/report path:

Qt views / PDF exporter
  -> ReportService
       -> const HotelManager aggregate

Persistence path:

DataManager
  <-> SQLite
  <-> HotelManager aggregate

Why this shape exists:
- Views collect input, provide feedback and render state. They must not become
  alternate business engines.
- Services own business invariants, validation and legal transitions.
- Managers are thin direct boundaries. BookingManager owns only BookingService
  and InvoiceService; CustomerManager owns only CustomerService; RoomManager owns
  only RoomService.
- HotelManager is a compatibility Facade for existing UI and a central aggregate
  owner. It constructs the relevant manager locally per facade operation.
- ReportService is intentionally not inside HotelManager because reporting is
  read-only and has independent aggregation rules.

Ownership:
- HotelManager owns shared_ptr vectors of Room, Customer, Booking and Invoice.
- Booking holds weak_ptr<Customer> and weak_ptr<Room>.
- Invoice holds weak_ptr<Booking> plus immutable copies of billable data.
- RoomMaintenance and MaintenanceGuestNotice are value records owned by manager.
- Qt owns child widgets through QObject parent-child ownership.
- Do not wrap a QObject child in std::shared_ptr; Qt already destroys it.

Design patterns and OOP concepts:
- Encapsulation: private fields, controlled ID setters, service-only mutation.
- Abstraction: Room exposes a virtual contract.
- Inheritance/polymorphism: StandardRoom, DeluxeRoom and SuiteRoom implement it.
- Factory: RoomFactory centralizes concrete room construction.
- Facade: HotelManager hides manager/service organization from views.
- Singleton: DataManager and StaffSession are single per-process contexts.
- DTO/read model: DashboardReportData and report entries isolate report shape.
- Composition: manager-service relationship is favored over deep inheritance.
- RAII: QObject parent ownership and smart pointers manage lifetimes.

===============================================================================
5. DOMAIN MODEL REFERENCE
===============================================================================

5.1 Room base class

Purpose:
Represents permanent room identity and commercial configuration. It deliberately
does not store current guest occupancy as a mutable boolean.

Fields:
- roomNumber: business identity of a room.
- basePrice: base nightly amount.
- isAvailable: permanent administrative sellability flag.
- archived: history-retention/non-operational flag.

Methods:
- setRoomNumber/getRoomNumber: write/read room identity.
- setBasePrice/getBasePrice: write/read base rate.
- setIsAvailable/getIsAvailable: permanent stop-sale control.
- isArchived/setArchived: archive lifecycle.
- calculateTargetPrice: virtual price after subtype fees.
- getRoomTypeName: virtual type label.
- getMaximumGuests: virtual capacity.
- getExtraFeeAmount/setExtraFeeAmount: virtual subtype fee access.

Important distinction:
getIsAvailable does not mean “the room is vacant now.” A permanently available
room can be occupied, reserved, awaiting arrival, or under dated maintenance.
Occupancy derives from Booking state and date. Maintenance is a separate interval.

5.2 Concrete room subclasses

StandardRoom:
- Implements base price as target price.
- Provides Standard type and its capacity.
- Extra fee access is neutral.

DeluxeRoom:
- Adds miniBarFee.
- calculateTargetPrice includes base price plus minibar fee.
- Returns Deluxe type, capacity and fee behavior.

SuiteRoom:
- Adds premiumServiceFee.
- calculateTargetPrice includes base price plus premium fee.
- Returns Suite type, capacity and fee behavior.

Changing a subtype price must not rewrite old invoices. New bookings quote the
current target price; existing active/completed bookings retain their quote.

5.3 RoomFactory and RoomType

RoomType enum currently includes Standard, Suite and Deluxe.
RoomFactory::createRoom(type, number, basePrice) creates the appropriate concrete
Room and returns shared_ptr<Room>. It prevents UI/database code from knowing
subclass constructors. Adding a new type requires:
1. enum extension;
2. factory creation;
3. UI type choice;
4. persistence mapping;
5. report labels;
6. pricing/capacity tests.

5.4 Customer

Fields:
- customerId: identity document/business key.
- name: display/legal customer name.
- phoneNumber: normalized international phone.
- archived: blocked from new operational bookings while retained historically.

Methods:
- default and value constructors.
- get/setCustomerId, get/setName, get/setPhoneNumber.
- isArchived/setArchived.
- isValid.

Customer names are not unique. Customer ID and normalized phone participate in
duplicate conflict policy. Customer does not own booking history; HotelManager
owns entities and query services derive related bookings.

5.5 Booking and BookingState

BookingState:
  UPCOMING
  ACTIVE
  COMPLETED
  CANCELLED
  NO_SHOW

Status is derived by HotelManager from persisted facts, not stored as an unrelated
free-text value. This reduces inconsistent state combinations.

Booking fields:
- bookingId.
- weak customer and room links.
- planned checkInDate/checkOutDate.
- cancelled and deleted legacy facts.
- checkedIn and checkedOut operational facts.
- actualCheckInDate and actualCheckOutDate.
- quotedUnitPrice and quotedTaxRate.
- adultCount and childCount.
- cancellationReason and cancelledAt.
- createdAt and updatedAt.

Methods:
- nextBookingId: returns next BK-numbered ID.
- initCounterFromDatabase: initializes static counter from DB maximum.
- getBookingId and private setBookingId.
- linked customer/room accessors.
- planned and actual date accessors.
- lifecycle fact accessors.
- getEffectiveCheckOutDate: actual checkout if present, otherwise planned end.
- rate/tax/count/reason/timestamp accessors.
- isValid: confirms linked weak references exist.

Private ID assignment prevents arbitrary UI identity changes. Booking setters are
data carriers, not lifecycle authorization. BookingService must remain the only
normal path for state transition.

5.6 Invoice

Fields:
- invoiceId and bookingId.
- weak booking link.
- taxRate, nights and invoiceIssuedDate.
- unitPrice.
- customerNameSnapshot, customerIdSnapshot, customerPhoneSnapshot.
- roomNumberSnapshot, roomTypeSnapshot.
- checkInDateSnapshot and checkOutDateSnapshot.

Methods:
- private setInvoiceId.
- booking link and field accessors.
- captureBookingSnapshot.
- calculateSubtotal: unitPrice * nights.
- calculateTotal: subtotal plus tax.
- generateInvoiceDetails.
- isValid.

Invoice snapshots are immutable-by-policy historical facts. They prevent later
changes to a customer, room name/type, room price or booking link from changing
a previously issued document. invoiceIssuedDate means issued, not paid.

5.7 RoomMaintenance and MaintenanceGuestNotice

RoomMaintenance models a [startDate, endDate) interval:
- maintenanceId, roomNumber, startDate, endDate, note, status, createdAt.
- isConfirmed returns true only for status "Confirmed".
- setStatus changes the workflow state.

MaintenanceGuestNotice models internal guest-contact work:
- noticeId, maintenanceId, bookingId, channel, status, loggedAt.
- Current channel value is “Simulated email”.
- It records a staff-visible work item, not actual delivery.

When maintenance overlaps unfinished bookings, the program creates Awaiting guest
response rather than immediately placing the room into actual Maintenance. The
pending case soft-holds new conflicting sales. After staff resolve affected
bookings, confirmation rechecks conflict and then turns it into a hard block.

6. SERVICE AND MANAGER API REFERENCE
===============================================================================

6.1 HotelManager

HotelManager owns collections, exposes read queries and facade mutations.

Collection/read methods:
- getRooms/getCustomers/getBookings/getInvoices return const collection references.
- getRoomMaintenances and getMaintenanceGuestNotices expose maintenance/log data.
- getMaintenanceGuestNotices(maintenanceId) filters notice records.
- clearAll resets aggregate before load/restore.
- roomNumberExists/customerIdExists/bookingIdExists/invoiceIdExists validate IDs.
- findRoomByNumber/findCustomerById/findBookingById/findInvoiceById return shared
  pointer or null; callers must handle null.
- findInvoiceForBooking enforces one-invoice-per-booking lookup.

Operational query methods:
- getAvailableRooms is a broad permanent-availability query, not a date-range
  booking answer.
- getBookingsForCustomer returns linked history.
- getTodayCheckIns/getTodayCheckOuts and date-specific arrival/departure queries
  support dashboard views.
- getBookingState is the state derivation authority.
- getRoomsByOccupancy derives current occupied/vacant room set.
- isRoomUnderMaintenance checks confirmed dated maintenance.
- hasRoomMaintenanceConflict checks a proposed interval, including pending soft hold.
- getBookingsByStatus filters derived state.

Facade mutation methods delegate to direct managers:
registerRoom, registerCustomer, updateCustomer, resolveCustomerForBooking,
createBooking, updateBooking, createInvoice, completeBooking, checkInBooking,
schedule/cancel/confirm maintenance, archive/restore/delete room/customer,
cancelBooking and markNoShow.

restoreBookingFromDatabase, restoreCustomerFromDatabase,
restoreInvoiceFromDatabase, restoreRoomMaintenanceFromDatabase and
restoreMaintenanceGuestNoticeFromDatabase are persistence restoration APIs only.
They must not become normal UI action APIs.

6.2 BookingManager and BookingService

BookingManager owns two immediate services and delegates:
createBooking, updateBooking, checkInBooking, cancelBooking, markNoShow,
completeBooking and createInvoice. It intentionally contains no QWidget, SQL or
message-dialog logic.

BookingService validation:
- validateBookingDates parses ISO YYYY-MM-DD and requires checkout > check-in.
- validateBookingInput requires customer/room existence, non-archived entities,
  permanent room availability, at least one adult, non-negative children, total
  capacity compliance, then asks RoomAvailabilityService.

Booking transition matrix:

From state    Action       Result          Key conditions
UPCOMING      Check in     ACTIVE          actual date=today; inside planned stay
UPCOMING      Cancel       CANCELLED       today before planned arrival
UPCOMING      No-show      NO_SHOW         today on/after planned arrival
ACTIVE        Check out    COMPLETED       actual out > actual in; out not future
COMPLETED     Edit         Rejected        historical record
CANCELLED     Edit         Rejected        cancellation retained
NO_SHOW       Check in     Rejected        no normal reversal path

createBooking:
- Rejects planned check-in in the past.
- Generates ID and initial lifecycle facts.
- Stores adult/child count and timestamps.
- Captures quoted room price and current tax (currently 10%).
- Does not create invoice or occupy room.

updateBooking:
- Rejects deleted, cancelled and completed bookings.
- Upcoming stays cannot move to a past arrival.
- Active stays cannot change guest, room or planned arrival.
- Active departure cannot be backdated.
- Availability excludes the booking being edited.
- Updating Upcoming refreshes quoted room price; Active preserves quote.

checkInBooking:
- Requires existing, unarrived, non-cancelled booking.
- Actual date must equal current date.
- Requires plannedIn <= today < plannedOut.
- Sets checkedIn, actualCheckInDate and updatedAt.

completeBooking:
- Requires ACTIVE state.
- Requires actual checkout > actual check-in and <= current date.
- Sets checkedOut, actualCheckOutDate and updatedAt.
- Does not record payment.

cancelBooking:
- Requires UPCOMING and current date before planned arrival.
- Retains cancellation reason, cancellation date and updatedAt.

markNoShow:
- Requires unarrived reservation on/after planned arrival.
- Retains cancelled facts and a reason beginning “No-show:”.

6.3 InvoiceService

createInvoice(invoiceId, bookingId, invoiceIssuedDate, error):
- requires non-empty/unique invoice ID;
- requires a valid ISO issue date;
- requires completed, non-deleted booking;
- enforces one invoice per booking;
- requires issue date between actual checkout and today;
- derives positive actual-stay nights;
- captures booked price/tax/customer/room/date snapshots.

The method deliberately does not accept UI-supplied amount, nights, tax or customer
text. This prevents an interface from creating financially inconsistent invoices.

6.4 RoomAvailabilityService

isRoomFreeForDates(room, checkIn, checkOut, error, excludedBookingId):
1. Checks maintenance conflict.
2. Ignores null, cancelled, deleted, completed and excluded booking records.
3. Finds same-room bookings through linked Room.
4. Blocks active stay relevant to today.
5. Applies half-open overlap formula:

  requestedCheckIn < existingCheckOut && existingCheckIn < requestedCheckOut

getAvailableRoomsForDates:
1. Validates date range.
2. Builds set of room numbers blocked by maintenance.
3. Scans bookings once and adds booking-blocked rooms.
4. Scans rooms once, returning only permanent-available/non-archived/unblocked.

This is the shared business truth. A new REST API, import tool, calendar sync or
batch job must call it or provide an equivalent database-level transaction guard.

6.5 CustomerManager and CustomerService

CustomerManager delegates registerCustomer, updateCustomer, resolveForBooking,
archiveCustomer, restoreCustomer and deleteCustomer.

CustomerService registration policy:
- Clear conflictingCustomerId output first.
- Find first phone and ID match.
- If phone + case-insensitive normalized name + ID match, report existing customer.
- If phone matches another record, report phone conflict.
- If ID matches another record, report ID conflict.
- Name alone is allowed to duplicate.
- On conflict, return conflicting customer ID so UI can highlight it.

updateCustomer excludes the record currently being edited before collision checks.
Do not duplicate these rules only in CustomerDialog because future import/API paths
would bypass UI validation.

6.6 RoomManager and RoomService

RoomManager delegates registerRoom, setAvailability, scheduleMaintenance,
cancelMaintenance, confirmMaintenance, archiveRoom, restoreRoom and deleteRoom.
RoomService delegates to HotelManager core so hierarchy remains one layer deep.

New room business rules, including future cleaning/inspection state, belong here
or in a dedicated domain service, not as direct widget mutations.

6.7 ReportService

Report DTOs:
- ReportRoomEntry: roomNumber, type, bookingCount.
- ReportBookingEntry: booking/customer/room/status/check-in/check-out display data.
- DashboardReportData: range, timestamps, counts, room-night denominators,
  occupancy values, invoice KPIs and sorted report lists.

buildDashboardReport(rangeIndex, rangeName):
- Creates a current timestamp and selected range label.
- Uses elapsedReportingWindow from range start through tomorrow, so future days
  are not included in period-to-date occupancy.
- Excludes archived rooms from room counts.
- Current occupancy uses active rooms at report generation.
- Period occupancy uses actual occupied room-nights.
- Completed-stay revenue uses immutable invoice totals when available.
- ADR divides invoice revenue by completed invoice nights.
- RevPAR divides invoice revenue by available room-nights.
- Sorts top rooms and booking lists deterministically.

===============================================================================
7. DATA FLOW, DATABASE SCHEMA, AND PERSISTENCE
===============================================================================

DataManager is the persistence gateway and one process-level singleton. It has:
- m_db: Qt SQL connection.
- m_dataPath: active database file.
- m_loadedRevision: revision of snapshot currently in memory.

Public API:
- getInstance: returns shared manager.
- loadAll: initializes/migrates DB, loads aggregate.
- saveAll: serializes current aggregate snapshot.
- commitChanges: saves current state or restores last saved state on failure.
- restoreLastSavedState: reloads last committed snapshot.

Core persistence tables:
- Customer: ID, name, phone, archived.
- Room: number, type, base price, subtype fee, permanent availability, archived.
- Booking: links, planned/actual dates, lifecycle flags, quote/tax, counts,
  cancellation fields and timestamps.
- Invoice: booking link, issue date, price/tax/nights and snapshots.
- RoomMaintenance: interval, note, status, creation time.
- MaintenanceGuestNotice: maintenance/booking link, simulated channel/status/time.
- Metadata/revision tables used for schema and stale snapshot protection.

Load order:
1. Open/init/migrate database.
2. Reconcile legacy duplicate customers.
3. Clear HotelManager.
4. Restore rooms and customers.
5. Restore bookings and resolve room/customer links.
6. Restore invoices and resolve booking links.
7. Restore maintenance and notices.
8. Initialize booking ID counter from maximum persisted BK ID.
9. Record loaded database revision.

Save order:
1. Start transaction and check revision.
2. Remove dependent rows in a safe order.
3. Save Customer and Room parents.
4. Save Booking rows.
5. Save Invoice, maintenance and notice dependent rows.
6. Advance revision and commit transaction.
7. On failure rollback and restore in-memory snapshot from DB.

Field flow summary:
- Customer ID/name/phone: dialog -> CustomerService -> Customer table; invoice
  copies snapshots at issuance.
- Room number/type/price/fee: RoomDialog -> Factory/service -> Room table; booking
  captures quote on create/edit Upcoming.
- Booking planned dates/counts: ReservationDialog -> BookingService ->
  AvailabilityService -> Booking table.
- Booking actual dates/lifecycle flags: check-in/out/cancel/no-show service -> DB ->
  Room Status/report/invoice behavior.
- Invoice snapshot: InvoiceService from completed Booking -> Invoice table ->
  dashboard/PDF. It is not recalculated from current Customer/Room.
- Maintenance/notice: Room workflow -> DB -> availability/Room Status/dialog.

The snapshot model is intentionally simple for the course project. It is not the
correct final architecture for concurrent reception terminals. Revision checking
helps detect obvious stale state but does not provide row-level optimistic locking,
distributed transaction control or conflict resolution.

===============================================================================
8. DETAILED OPERATIONAL FLOWS
===============================================================================

Customer creation/edit:
CustomerPageWidget opens CustomerDialog. CountryInputRules provides country code,
calling code, compact hint, regex and expected local length. Dialog normalizes
phone formatting and leading zeroes. CustomerService applies duplicate policy.
On conflict, page highlights the matching record. On success, caller commits and
refreshes. Archive retains record/history but blocks new or edited bookings.

Room and maintenance:
RoomPageWidget opens RoomDialog. RoomFactory creates correct subtype on add.
Permanent availability is an administrative stop-sale flag, not a short repair
or guest occupancy. A conflict-free maintenance interval is Confirmed immediately.
An overlapping unfinished booking creates Awaiting guest response plus one
MaintenanceGuestNotice per affected booking. Staff resolve conflicts, then
confirm; confirmation rechecks live overlap. Pending and confirmed intervals both
block new overlapping bookings, but only confirmed interval shows Maintenance.

Reservation creation:
Room Status is the deliberate only normal entry point. Staff selects room,
MainWindow routes room number, Reservations page opens ReservationDialog with room
preselected. The dialog collects customer, planned dates and guest counts and
queries available rooms. BookingService repeats critical validation before adding
UPCOMING booking and locking price/tax. The caller commits and emits refresh signals.

Reservation editing:
Upcoming booking may be edited if future-valid and available. Active booking
cannot change customer, room or planned arrival. Completed/cancelled/no-show
records are not normally editable. This protects operational facts and invoice
history. A future room move should be a separate audited workflow, not a relaxed
edit rule.

Check-in:
The system never turns a booking Active based solely on date. Staff must confirm
check-in on current date. The state becomes ACTIVE and Room Status derives
Occupied from that fact.

Checkout:
Staff can complete only ACTIVE booking. Actual departure must follow actual
arrival and not be future. Completion is followed by invoice creation using
actual duration and quote snapshot. Invoice issuance is not payment collection.

Cancellation/no-show:
Cancellation is only before planned arrival. No-show is only on/after planned
arrival for unarrived guest. Both preserve reason/date so history distinguishes
guest cancellation from non-arrival.

Reporting:
Dashboard and PDF use ReportService snapshot. Current occupancy is point-in-time;
period occupancy is actual room-nights to date. Revenue/ADR/RevPAR are invoice
metrics. Booking History uses actual checkout in selected period and paginates
seven records per page.

===============================================================================
10. RISK REGISTER
===============================================================================

HIGH: Payment/folio is absent.
Invoice means an amount was issued, not collected. There is no method, deposit,
partial payment, balance, refund, discount or surcharge. Correct future model:
Folio per booking, immutable Payment events, derived balance, explicit checkout
policy for paid-in-full versus open balance.

HIGH: Authentication and audit are incomplete.
Bootstrap login is not authorization. Add Staff records, per-user strong password
hashes, role checks at service boundary and immutable AuditLog (actor, action,
entity, time, before/after summary, correlation ID).

HIGH: Snapshot persistence is not multi-user safe.
Two terminals or copied DB files can diverge and local counters can collide.
Scale through shared server DB/API, targeted transactional repository commands,
row versions and overlap protection inside the transaction.

HIGH: Simulated notice is not delivery.
The log intentionally does not claim email delivery. A real provider integration
needs an adapter, outbox, retries, idempotency, delivery/failure status, consent
and PII policy.

MEDIUM: Housekeeping state machine is absent.
Do not overload Room::isAvailable. Add separate Dirty, Cleaning, Inspected and
OutOfOrder states. Checkout should transition to Dirty; sellable availability
should require an inspected room plus no booking/maintenance block.

MEDIUM: Time authority is local workstation clock.
QDate::currentDate affects check-in, checkout, no-show and reporting. Use an
injectable Clock for tests and centralized hotel timezone/source for production.

MEDIUM: Privacy/security controls are limited.
SQLite contains ID/phone data. Add access control, secure backup, retention,
anonymization, export minimization and encryption-at-rest when required.

MEDIUM: Legacy UI can drift.
bookingdialog.* and ReservationDialog must not become two independent workflows.
Remove/archive the legacy path once references are confirmed.
